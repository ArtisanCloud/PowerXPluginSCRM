## Clarifications

### Session 2026-03-23

- Q: 欢迎语同步到企业微信的触发策略是什么？ → A: 保存后不自动同步，必须人工点击发布同步。
- Q: 欢迎语内容形态（MVP）采用哪种范围？ → A: 完全跟随企业微信原生能力，不做平台侧消息形态限制。
- Q: 同一线索多次由不同渠道码触达时，主归因如何确定？ → A: 采用首触归因优先，同时保留全部触达映射记录。
- Q: 欢迎语同步失败后的重试策略是什么？ → A: 自动重试 3 次（短间隔），失败后转人工重试。
- Q: 谁有权限触发欢迎语发布同步？ → A: 租户管理员与渠道运营角色可触发发布同步。
- Q: 短间隔自动重试的默认时长是什么？ → A: 默认 5 秒、15 秒、30 秒三次退避重试（可配置覆盖）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置渠道码与专属欢迎语 (Priority: P1)

作为运营人员，我需要为不同渠道码分别配置欢迎语并启停渠道码，以便不同投放入口有不同接待话术和运营策略。

**Why this priority**: 没有可配置的渠道码与欢迎语，就无法形成“按入口差异化运营”的最小业务价值。

**Independent Test**: 仅交付“创建渠道码、配置欢迎语、启停渠道码、回显配置”即可独立验收，并可用于真实运营配置。

**Acceptance Scenarios**:

1. **Given** 租户下已存在可用渠道账号，**When** 运营人员创建两个渠道码并分别保存不同欢迎语，**Then** 系统可以分别回显两套配置且互不覆盖。
2. **Given** 某渠道码处于启用状态，**When** 运营人员将该渠道码切换为停用，**Then** 新增引流事件不再按该渠道码进入有效引流流程，并记录状态变更。

---

### User Story 2 - 事件入池与来源追溯 (Priority: P1)

作为线索管理员，我希望来自渠道码的触达事件能稳定进入线索采集链路并保留来源追溯，以便后续分配、转化与复盘。

**Why this priority**: 渠道码价值的核心在于带来可追溯线索；如果没有事件入池与归因，渠道码只是配置功能。

**Independent Test**: 仅交付“事件接入、重复事件去重、线索入池、来源追溯查询”即可独立证明业务闭环。

**Acceptance Scenarios**:

1. **Given** 某渠道码收到首条有效触达事件，**When** 系统处理该事件，**Then** 产生对应线索记录并保留渠道码来源信息。
2. **Given** 同一事件被渠道重复投递，**When** 系统再次接收该事件，**Then** 不重复写入业务结果且可查询到幂等命中记录。

---

### User Story 3 - 欢迎语同步渠道与状态可见 (Priority: P2)

作为运营负责人，我希望欢迎语配置可以发布到渠道侧并可查看同步状态，以便确认配置是否真正生效。

**Why this priority**: 配置保存不代表渠道生效；缺少同步状态会导致运营执行不可控。

**Independent Test**: 仅交付“触发同步、查看同步状态、查看失败原因”即可独立验证可运维性。

**Acceptance Scenarios**:

1. **Given** 某渠道码已配置欢迎语，**When** 运营人员触发同步，**Then** 系统返回该配置的最新同步状态与时间。
2. **Given** 渠道侧拒绝同步请求，**When** 运营人员查看同步状态，**Then** 系统显示失败状态与可读失败原因，且不丢失原配置。

---

### Edge Cases

- 当渠道码未绑定有效目标群或目标入口时，系统如何阻止发布并给出可操作提示？
- 当欢迎语内容超出渠道允许范围时，系统如何拒绝保存或提示修正？
- 当同一租户短时间内批量触发同步时，系统如何避免状态混乱并保持每个渠道码状态可追踪？
- 当渠道账号失效后，已有渠道码配置如何标记为不可同步并提示运营处理？
- 当线索已由渠道码 A 入池后又从渠道码 B 再次触达时，系统如何保留多来源追溯关系且不破坏去重结果？

## Requirements *(mandatory)*

### Assumptions & Dependencies

- 已具备可用的渠道账号治理能力，且可识别不同渠道账号归属。
- 线索采集链路已支持基础入池、去重和来源字段存储能力。
- 运营角色具备渠道码配置与同步操作权限，审计能力可记录关键操作。
- 本期以企业微信为首个落地渠道，其他渠道按统一规则后续扩展。

### Out of Scope

- 欢迎语智能编排、自动优化和 A/B 策略实验。
- 多目标复杂分流（同一渠道码按规则路由多个目标）。
- 渠道外的跨平台统一群运营自动化能力。

### Functional Requirements

- **FR-001**: 系统必须允许运营人员创建、查询、启用和停用渠道码。
- **FR-002**: 系统必须支持为每个渠道码单独配置欢迎语，且不同渠道码配置相互隔离。
- **FR-003**: 系统必须保留渠道码配置的最近一次变更记录（变更人、变更时间、变更摘要）。
- **FR-004**: 系统必须在渠道码停用后阻断其新增引流事件进入有效引流流程。
- **FR-005**: 系统必须接收渠道触达事件并识别其对应渠道码。
- **FR-006**: 系统必须对渠道事件执行幂等判定，确保重复投递不重复产生业务结果。
- **FR-007**: 系统必须将有效渠道事件写入线索采集链路，并保留可追溯来源信息。
- **FR-008**: 系统必须支持从线索侧反查其关联渠道码与来源触达事件。
- **FR-009**: 系统必须支持按渠道码由人工触发欢迎语同步，并返回同步任务结果。
- **FR-010**: 系统必须为每个渠道码维护欢迎语同步状态（未同步、同步中、成功、失败）及最近错误信息。
- **FR-011**: 系统必须在同步失败时保留原欢迎语配置，不得自动清空或覆盖。
- **FR-012**: 系统必须支持按租户维度的数据隔离与权限隔离，避免跨租户访问渠道码和事件数据。
- **FR-013**: 系统必须对渠道码配置、欢迎语修改、同步触发、同步失败等关键动作记录审计信息。
- **FR-014**: 系统必须允许运营人员查看渠道码的引流事件列表与基础统计（触达量、入池量、去重量）。
- **FR-015**: 系统必须在渠道账号不可用时阻止同步并给出明确可操作提示。
- **FR-016**: 系统必须定义统一渠道码与欢迎语能力契约，使后续新增渠道时不改变业务使用方式。
- **FR-017**: 系统必须保证“保存配置”与“发布同步”是两个独立动作；保存成功不得被视为渠道侧已生效。
- **FR-018**: 系统必须在欢迎语发布前执行渠道兼容性校验，并在校验失败时返回可读错误（不改变已保存配置）。
- **FR-019**: 系统必须支持线索与渠道触达记录的多对多映射关系，完整保留历史触达链路。
- **FR-020**: 系统必须为每条线索维护唯一“主归因记录”，主归因按首触规则确定；后续触达不得覆盖主归因，但必须追加映射记录。
- **FR-021**: 系统必须在欢迎语同步失败后自动执行最多 3 次退避重试（默认间隔 5 秒、15 秒、30 秒，可配置）；超过重试上限后标记为“需人工处理”，并允许人工再次触发同步。
- **FR-022**: 系统必须仅允许“租户管理员”和“渠道运营角色”触发欢迎语发布同步，其他角色只能查看状态不可发布。
- **FR-023**: 系统必须定义并返回欢迎语发布失败的标准错误分类，至少包含：`UNSUPPORTED_MESSAGE_TYPE`、`CHANNEL_AUTH_INVALID`、`CHANNEL_RATE_LIMITED`、`CHANNEL_REJECTED`、`CHANNEL_UNAVAILABLE`。

### Key Entities *(include if feature involves data)*

- **渠道码（Channel Code）**: 表示可投放的引流入口，包含所属租户、所属渠道账号、状态与目标绑定信息。
- **渠道码欢迎语配置（Code Welcome Configuration）**: 表示某个渠道码专属的欢迎语内容及其启用状态、最近同步状态。
- **渠道触达事件（Code Touch Event）**: 表示通过渠道码触发的扫码、入群、触达等事件，用于入池和统计。
- **线索来源追溯记录（Lead Attribution Record）**: 表示线索与渠道码事件之间的映射关系；同一线索可关联多条记录，其中一条标记为主归因（首触）。
- **欢迎语同步记录（Welcome Sync Record）**: 表示欢迎语发布到渠道侧的执行结果与失败原因历史。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营人员可在 3 分钟内完成单个渠道码从创建到欢迎语配置的完整操作。
- **SC-002**: 95% 以上的有效渠道触达事件可在 60 秒内完成入池并可被来源追溯查询。
- **SC-003**: 重复投递事件导致的重复业务写入率为 0。
- **SC-004**: 运营人员对“欢迎语是否已在渠道侧生效”的状态判断准确率达到 100%（以系统同步状态为准）。
- **SC-005**: 90% 以上的欢迎语同步失败场景可在界面中看到明确失败原因并可再次触发同步。
- **SC-006**: 在上线后一个运营周期内，渠道码来源线索的可追溯覆盖率达到 99% 以上。

## V2 对齐补充（员工活码独立域）

> 本节用于对齐 2026-03-25 的产品决策：在 `005` 内新增“引流获客”重构范围。  
> 既有 V1（通用 channel-code）实现记录保留，不作为本节改造阻塞项。

### V2 业务目标

- 将“员工活码”从通用渠道码能力中拆出为独立业务域，形成可独立演进的模型与 API。
- 第一版交付“员工活码 + 员工欢迎语”全量可用能力。
- “群活码 + 群欢迎语”先交付模型/API/页面骨架，后续接入企业微信群活码实装能力。

### V2 交付范围

- 新增引流获客菜单下四个子页面并消除占位页：
  - 员工活码
  - 员工欢迎语
  - 群活码（骨架）
  - 群欢迎语（骨架）
- 员工活码页面采用“列表页 + 设置页”结构，设置页包含：
  - 基础设置（活码名称、选择成员、企业微信标签、客户备注开关）
  - 回复设置（员工欢迎语 / 不发欢迎语）
  - 右侧手机预览
- 员工欢迎语采用“结构化编辑 + JSON 预览”模式，不采用纯 JSON 裸编辑作为主交互。

### V2 关键规则

- 员工成员选择数据源固定为 `org_sync` 已确认映射成员（confirmed mapping），不做实时企业微信拉取。
- “保存配置”与“发布同步”继续保持分离动作。
- 员工活码与群活码采用独立模型，不复用 V1 的 `ChannelCode` 作为主存储。
- 群能力在本期可返回 `not_implemented` 能力标记，但页面与接口必须可访问且非空白。

### V2 Functional Requirements

- **FR-024**: 系统必须提供员工活码独立数据模型与接口（创建、列表、详情、更新、状态切换）。
- **FR-025**: 系统必须提供员工欢迎语独立配置模型与接口（保存、查询、发布、发布状态）。
- **FR-026**: 系统必须支持员工活码设置页的“结构化编辑 + JSON 预览”，并在提交前完成合法性校验。
- **FR-027**: 系统必须仅允许从 `org_sync` 已确认映射成员中选择员工成员，未确认映射成员不得提交成功。
- **FR-028**: 系统必须提供群活码与群欢迎语的独立模型/API/页面骨架，并明确能力状态可见。
- **FR-029**: 系统必须保证引流获客四个子菜单均有可访问页面，不得回落到通用占位页。
- **FR-030**: 系统必须保持 V1 已上线通用渠道码能力可继续运行，直到 V2 完成迁移切换。

### V2 Success Criteria

- **SC-007**: 引流获客四个子菜单均可访问且页面首屏渲染成功率达到 100%。
- **SC-008**: 运营人员可在 5 分钟内完成“员工活码创建 -> 员工欢迎语保存 -> 发布 -> 状态查询”。
- **SC-009**: 员工成员选择的无效提交（非 confirmed mapping）拦截率达到 100%。
- **SC-010**: 群活码/群欢迎语页面在本期无空白页，均展示可操作骨架与能力状态说明。

### V2 页面交互对标补充（2026-04-29）

- 本节用于对齐“员工活码设置页”对标交互，确保运营页面从工程态输入升级为业务态配置。
- 对标范围仅覆盖 `员工活码设置页`，不改变后端实体边界（仍沿用 `staff_live_codes + staff_welcome_configs`）。

#### V2 页面结构要求

- 设置页必须采用双栏结构：
  - 左栏：基础设置 + 回复设置；
  - 右栏：手机预览（实时映射左栏配置）。
- 基础设置区必须包含：
  - 活码名称；
  - 选择企业成员（按钮 + 已选人数 + 成员清单）；
  - 企业微信标签（标签选择器 + 已选标签展示）；
  - 客户备注（开关 + 备注位置 + 备注文案预览）。
- 回复设置区必须包含：
  - 欢迎语模式：`员工欢迎语` / `不发欢迎语`；
  - 回复内容块：`文本`、`图片`、`链接`、`小程序`；
  - 雷达关联入口（可先提供占位选择器，但字段需落库并可回显）。

#### V2 页面交互约束

- 成员与标签输入不得要求用户手工输入 UUID/TagID。
- 成员选择器数据源必须是 `org_sync confirmed mapping`。
- 标签选择器必须展示“标签组 + 标签名”可读信息，提交时再映射为 tag id。
- “保存配置”与“发布同步”必须是两个独立按钮，页面必须展示最近同步状态与失败原因。
- “添加回复内容”下拉菜单不得出现定位错位或被容器裁切；必须满足：
  - 下拉锚定按钮；
  - 不遮挡主操作按钮；
  - 在常见桌面分辨率下无错位（含 125% 浏览器缩放）。

#### V2 Functional Requirements（页面对标）

- **FR-031A**: 系统必须提供员工活码设置页双栏布局（左配置右预览），并支持实时预览。
- **FR-031B**: 系统必须使用结构化成员选择器与标签选择器，禁止主流程依赖手工 ID 输入。
- **FR-031C**: 系统必须支持欢迎语内容块类型：文本、图片、链接、小程序，且可组合保存与回显。
- **FR-031D**: 系统必须提供“保存配置/发布同步”双动作与同步状态可视化（状态、时间、错误）。
- **FR-031E**: 系统必须修复回复内容下拉浮层错位问题，保证定位和层级稳定。

#### V2 Success Criteria（页面对标）

- **SC-010A**: 运营人员无需手工输入 UUID/TagID 即可完成配置，相关输入依赖降为 0。
- **SC-010B**: 回复内容下拉菜单在主流桌面分辨率与 125% 缩放下显示正确率达到 100%。
- **SC-010C**: 运营人员可在 5 分钟内完成“设置成员/标签 -> 设置欢迎语内容块 -> 保存 -> 发布 -> 查看状态”闭环。

## V2.1 对齐补充（群运营闭环：活码优先）

> 本节为 2026-04-19 新增对齐，基于已落地 V2（员工全量 + 群骨架）继续推进。  
> 目标：将“群运营”从骨架升级为可运营闭环。

### V2.1 交付原则

- 不是技术强依赖，但产品闭环优先级为：`群活码 -> 群聊同步 -> 本地群标签 -> 群运营分析`。
- 群标签定义为“平台本地运营标签”，不承诺回写企业微信官方群标签（官方无对应写接口）。
- 与企业微信回写相关能力仅包含：群活码（入群方式）与群信息同步，不包含官方群标签回写。

### V2.1 业务范围

- 群活码（入群方式）全量能力：
  - 新建、查询、更新、删除、启停、有效期管理；
  - 支持 `config_id/state` 存储与回显。
- 群聊同步全量能力：
  - 周期拉取：`groupchat/list + groupchat/get`；
  - 增量接收：客户群变更事件回调；
  - 建立 `chat_id` 主数据。
- 本地群标签能力：
  - 手工标签 CRUD；
  - 群与标签绑定关系管理；
  - 基于来源活码/群主/成员结构规则自动打标（首批规则化）。
- 群运营分析能力：
  - 群列表筛选、统计、导出；
  - 按活码来源（`config_id/state`）看拉群效果与质量。

### V2.1 Functional Requirements

- **FR-031**: 系统必须提供群活码（入群方式）独立 CRUD 能力，并保存渠道侧 `config_id`、`state`、`qr_code` 与状态字段。
- **FR-032**: 系统必须支持群活码的“保存配置”与“发布到渠道”分离动作；发布失败时保留本地配置。
- **FR-033**: 系统必须支持群活码发布同步状态机（`pending|syncing|success|failed|manual_required`）与失败原因记录。
- **FR-034**: 系统必须支持群聊主数据同步，至少覆盖：`chat_id`、群名、群主、成员数、建群时间、最近同步时间、活跃时间。
- **FR-035**: 系统必须支持通过客户群变更回调更新群主数据，并与拉取任务口径一致。
- **FR-036**: 系统必须提供本地群标签（标签定义 + 绑定关系）管理能力，且严格租户隔离。
- **FR-037**: 系统必须支持按规则自动打本地群标签，首批规则至少包含：来源活码、群主、成员结构（客户标签占比）。
- **FR-038**: 系统必须提供群运营查询与筛选，至少支持：标签、群主、来源活码、成员规模、时间区间。
- **FR-039**: 系统必须支持群运营数据导出，导出口径与页面筛选条件一致。
- **FR-040**: 系统必须明确标注“本地群标签不回写企业微信”，避免用户误解为官方标签同步。
- **FR-041**: 系统必须在客户群成员新增回调事件到达后，按 `chat_id + external_userid` 触发增量补打企业标签，覆盖“发布后新入群成员”场景。
- **FR-042**: 系统必须支持自建应用与代开发应用“不同回调入口、统一业务分发”架构；两种入口解析后进入同一客户入群补打标逻辑。
- **FR-043**: 系统必须为客户入群增量打标定义幂等口径（至少包含 `corp_id/chat_id/external_userid/event_type/event_time`），重复回调不得重复造成业务副作用。

### V2.1 Success Criteria

- **SC-011**: 运营人员可在 5 分钟内完成“创建群活码 -> 发布 -> 查看状态 -> 关联群列表”闭环。
- **SC-012**: 95% 以上群聊主数据可在 10 分钟内完成拉取或回调更新入库。
- **SC-013**: 群运营列表筛选结果与导出结果一致率达到 100%。
- **SC-014**: 自动打标规则命中日志可追溯率达到 100%（含规则版本、命中原因、执行时间）。
- **SC-015**: 页面中“本地群标签”与“渠道同步字段”区分明确，误操作工单占比低于 5%。
- **SC-016**: 发布后新增入群成员在回调到达后可自动完成企业标签补打，成功率达到 95% 以上（权限错误类除外）。

## V2.2 对齐补充（群成员客户档案增强）

> 本节为 2026-04-20 新增对齐，目标是将“群成员 -> 客户详情”从轻量弹窗升级为可运营档案视图。  
> 说明：V2.2 在 V2.1 闭环基础上追加，不阻塞群活码/群标签主流程。

### V2.2 业务目标

- 在群管理详情内提供更接近企业微信工作台的客户档案体验（所属群聊、客户动态、跟进记录）。
- 明确“当前可展示数据”与“待接入业务域数据”的边界，避免伪造状态或误导用户。
- 统一主详情与客户详情的信息密度、视觉层级与交互节奏。

### V2.2 交付范围

- 群详情弹窗增强：
  - 大尺寸抽屉/弹窗（支持滚动、分页）；
  - 群级指标卡（今日入群、今日退群、成员总数）；
  - 成员明细表与成员分页。
- 客户详情弹窗增强：
  - 结构化头部（身份、userid、所属关系）；
  - 标签页：`基础信息`、`所属群聊`、`客户动态`、`跟进记录`（后两者可先接占位状态机）；
  - 可扩展至订单/购物车等跨域信息位。
- 事件与动态数据：
  - 群成员加入事件时间线（至少“加入群聊”事件）；
  - 统一事件模型，支持后续接入好友添加、标签变更、跟进行为等。

### V2.2 Functional Requirements

- **FR-041**: 系统必须支持群管理列表分页，默认每页 10 条，并保持筛选条件与分页状态一致。
- **FR-042**: 系统必须在群列表提供 `今日入群` 与 `今日退群` 指标列，计算口径需可追溯。
- **FR-043**: 系统必须在主列表隐藏 `chat_id`，仅在详情中展示，减少运营主视图噪音。
- **FR-044**: 系统必须将群详情弹窗升级为大尺寸信息面板，支持成员分页浏览。
- **FR-045**: 系统必须提供客户详情标签页结构，至少包含 `基础信息` 与 `所属群聊` 可用内容。
- **FR-046**: 系统必须为 `客户动态` 与 `跟进记录` 提供统一事件模型与占位状态（未接入时明确提示）。
- **FR-047**: 系统必须支持从群成员记录跳转/打开客户详情，不得丢失当前群上下文。
- **FR-048**: 系统必须对“已接入数据”与“待接入数据”进行显式区分，不得展示误导性空白成功态。

### V2.2 Success Criteria

- **SC-016**: 群管理页主列表到客户详情链路（列表 -> 群详情 -> 客户详情）操作成功率达到 100%。
- **SC-017**: 用户在 3 次点击内可定位到目标成员的基础资料与所属群关系。
- **SC-018**: 群详情与客户详情弹窗在 1080p 分辨率下无需横向滚动即可完成核心信息浏览。
- **SC-019**: “未接入数据”提示覆盖率达到 100%，避免出现无说明空白区。

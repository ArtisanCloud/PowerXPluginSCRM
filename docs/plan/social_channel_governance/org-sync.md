# 组织架构同步与映射（多渠道账号）

## 背景
线索接入会涉及企业微信、钉钉等多个渠道账号。实际业务上一个租户只应有一套“主组织架构”（部门 + 成员），渠道侧组织数据只作为来源信息，不能直接覆盖主组织。

## 目标
- 为多渠道账号建立统一的组织映射逻辑
- 支持 Standalone 与宿主模式的组织架构兼容
- 为线索归属、负责人分配、账号权限等提供稳定的主组织视图

## 范围
- 组织架构来源同步（企业微信/钉钉等）进入“来源层”
- 组织/成员映射到主组织的规则与流程
- 映射确认后的业务视图（供线索分配、权限、账号归属使用）

## 非目标
- 替换宿主模式的底座组织架构
- 直接覆盖主组织数据（强同步）
- 同步薪资、绩效等非 SCRM 业务字段
- 渠道侧组织回写/双向同步（作为独立 feature 另行设计）

## 模式约束
- Standalone：使用插件内 IAM 表（`iam_departments / iam_members / iam_users / iam_roles...`）
- 宿主模式：使用 PowerX 底座组织架构表（同名概念，但表位于宿主）
- **无论模式如何，主组织只有一套**

## 核心原则
- 渠道同步“只写来源层”，不直接写主组织
- 映射层决定“来源 -> 主组织”的归属关系
- 线索与业务权限只依赖“主组织成员”
- 多渠道/多账号必须按 `channel_account_uuid` 分区存储与展示

## 渠道账号与默认组织来源
- 一个租户可绑定多个渠道账号，但每个渠道应明确一个“默认组织来源账号”。
- 默认组织来源可切换，切换仅影响默认展示与默认同步入口，不影响历史数据。
- 登录与授权必须绑定 `channel_account_uuid`（建议提供选择入口或独立入口）。

## 员工账号绑定与引导策略
为保证线索分配与成员匹配可用性，需要引导员工完成渠道账号绑定。

推荐策略：
- **软引导**：员工首次进入 SCRM 时若未绑定任何渠道账号，弹出引导提示（允许稍后）。
- **功能硬限制**：未绑定用户不可作为线索/客户负责人候选。
- **个人资料页入口**：提供“我的账号”页面查看/新增绑定（支持多渠道）。
- **管理视图**：管理员可查看绑定覆盖率与未绑定名单。

## 数据模型（建议）
> 以下是概念结构，具体表名可按插件规范落表。

- org_source_accounts  
  - 绑定渠道账号（provider/app/account_uuid）
  - 标识来源账号范围与同步策略

- org_source_units  
  - 渠道同步的部门/组织节点（原始层）

- org_source_members  
  - 渠道同步的成员/员工（原始层）

- org_unit_mappings  
  - 来源部门 -> 主组织部门

- org_member_mappings  
  - 来源成员 -> 主组织成员
  - 支持一对多、多对一（同一成员多个渠道身份）

> 统一约束：来源层与映射层都必须带 `tenant_uuid`，使用插件 schema（`powerx_plugin_base`），启用 RLS。
> 宿主模式下，主组织来自宿主表，插件只维护来源层与映射层。

## 同步流程
1. 渠道账号同步组织数据 → 写入 `org_source_units / org_source_members`
2. 执行自动匹配（手机号/邮箱/外部ID）
3. 未匹配项进入“人工确认”列表
4. 映射确认后，业务侧使用主组织视图

## 接口与后台能力（规划）
- 同步入口：按租户 + 渠道账号触发同步
- 映射管理：来源部门/成员查询、匹配建议、人工确认
- 映射状态：已匹配/待确认/冲突
- 只读视图：主组织 + 来源身份的统一视图

## 管理台页面与流程（规划）
1. 选择渠道账号（联动下拉：渠道 → app_type → 账号）
2. 点击“同步组织与成员”（异步执行）
3. 展示同步结果日志（成功/失败/耗时/部门数/成员数/新增/更新/冲突/待确认）
4. 处理映射修正（冲突/未匹配）
5. 去重与合并（重复候选展示）

> 同步方向：单向（渠道账号 → 来源层）。不回写渠道账号；映射确认仅影响主组织视图。
> 若需要回写渠道侧组织与成员，需在独立 feature 中补充权限、冲突策略与审计流程。

## 渠道驱动与 SDK 接入方案（补充）
目标：引入“渠道驱动层”解耦不同 SDK，实现统一同步流程。

### 驱动层设计
- 统一接口 `OrgSyncDriver`
  - `FetchDepartments(account)` → 返回 `SourceUnitDTO[]`
  - `FetchMembers(account)` → 返回 `SourceMemberDTO[]`
- `DriverRegistry` 按 `channel + app_type` 注册驱动
- 统一错误与字段映射策略（auth/perm/rate_limit/invalid）

### 企业微信（PowerWechat SDK）
- SDK：PowerWechat（Go）
- 适配器实现：
  - `department/list` → 来源部门
  - `user/list` 或 `user/list_id` → 来源成员
- 关键字段：
  - 企业 ID（CorpID，企业级）
  - 应用 AgentID + 通讯录管理 Secret（应用级）
  - `user_id` 作为 `external_member_id`
  - 通讯录管理 Secret 可在账号创建时暂不填写，但同步/测试会失败并返回提示

### 企业微信策略调整（政策限制）
根据企业微信“通讯录同步接口调整”：
- **通讯录同步 Secret** 在新 IP 下仅能获取 ID（`userid/department_id`），不可获取成员详情。
- 读取成员详情需使用 **自建应用**（App Secret + AgentID），敏感字段需 OAuth2 授权补全。

推荐策略：
- **ID-only 同步**：`user/list_id` + `department/simplelist` → 仅同步 ID 与部门关系。
- **详情补全**：用户/管理员 OAuth 授权后补全敏感字段（手机号/邮箱/头像等）。
- **多账号并存**：每个企业微信账号单独存储来源层数据，统一映射到主组织。

### 同步服务落地
- `TriggerSync` 读取渠道账号配置 → 选择 driver
- 拉取组织/成员 → Upsert 写入来源层
- 统计新增/更新/冲突/待确认 → 写入 `sync_log` 与 `source_account.last_sync_*`

### 多渠道扩展
- 钉钉（DingTalk SDK）
- 飞书（Lark SDK）
- 其他服务平台只需实现 driver 接口即可接入

## 风险与对策
- 多账号重复成员：以手机号/邮箱优先匹配，冲突进入人工确认
- 渠道字段缺失：允许跳过并标记为“待补全”
- 宿主模式差异：通过适配层屏蔽底座表结构差异

## 验收标准
- 支持一个租户多渠道账号同步到来源层
- 映射确认后可在“主组织视图”查询到成员
- 线索分配只使用主组织成员，不直接使用来源成员

## 任务拆解（Draft）
### Phase 1 - 数据与基础能力
- T1: 定义来源层与映射层数据结构（表常量、模型、迁移、RLS）
- T2: Source 同步入口（按租户 + 渠道账号触发）
- T3: 来源组织/成员查询 API（分页 + 过滤）

### Phase 2 - 映射与确认
- T4: 自动匹配策略（手机号/邮箱/外部ID）
- T5: 映射确认 API（单条/批量）
- T6: 冲突与待确认列表

### Phase 3 - 主组织视图与应用
- T7: 主组织视图接口（主组织 + 来源身份聚合）
- T8: 线索分配仅使用主组织成员验证
- T9: 管理台映射维护页面（只读/确认/搜索）

## 映射策略建议
- 优先：手机号、邮箱
- 次级：渠道内唯一ID（企微 user_id / 钉钉 userid）
- 无匹配时由管理员确认并生成映射

## 对线索系统的影响
- 线索归属只绑定主组织成员（member_id）
- 渠道账号仅作为来源字段记录
- 若渠道账号下新增成员，需通过映射确认后才能参与分配

## 与企业微信线索拉取的关系
企业微信线索拉取前需完成组织同步与映射能力，否则无法稳定地将线索归属到主组织成员。

## 宿主模式菜单建议
- 主组织入口由 PowerX 底座提供，插件不重复建设“组织架构管理”
- 插件侧菜单仅保留与渠道映射相关的能力：
  - 渠道组织同步
  - 组织映射管理
  - 同步状态与冲突处理
